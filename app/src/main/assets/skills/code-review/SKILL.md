## 代码审查（Code Review）

把「我觉得没问题」变成结构化的六维审查，不放过回归与隐患。

## 何时触发

- 用户完成一组改动、准备提交
- 用户说「审查」「review」「帮我看看」「这改动行不行」
- 改动触及敏感面（启动/容器/签名/CI/数据库迁移）时主动建议先审

## 工作流

1. 用 git diff / `readFile` 圈定本次改动范围，读到确切原文再判断，不要凭记忆。
2. 顺着调用关系往上下游各走一层，确认改动不会在别处炸（谁调它、它调谁）。
3. 按六维逐条过，每条问题带 `文件:行号`：
   - **正确性**：逻辑错？边界（空/0/负/超大/null）？回归？
   - **设计**：职责单一？重复代码？耦合？扩展性？
   - **可读性**：命名？超长函数/深嵌套？注释该不该有？
   - **测试**：有且有效？覆盖边界与错误路径？
   - **规范**：遵循项目约定（命名/API 返回格式/日志）？死代码/调试输出？
   - **性能安全**：瓶颈（循环查库/全表扫/内存泄漏）？漏洞（注入/XSS/硬编码密钥/权限不严）？
4. 触碰项目硬约束（`targetSdk 28`、迁移编号连续、双语 `strings.xml`、`prompts/`/文档同步）必须标红。

## 产出

- 问题清单按「必须修 / 建议改 / 可选」分档。
- 每条：`文件:行号` + 问题 + 为什么是问题 + 建议方向（不给完整代码）。
- 无问题的维度写「无显著问题」，别省略。
- 读到的与推断的区分，推断标「未核实」。
- 整体一句结论（能否提交）+ 必须修的项数。
- 改动触及敏感面时，建议发版先发 RC。
